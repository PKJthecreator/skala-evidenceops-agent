# Ollama 캡처 6장 검토 — 2026-10-20

사용자가 지정한 `운영 에이전트 캡쳐 사진/ollma 사용 시` 폴더의 PNG 6개를 직접 확인했다. 원본 이미지는 변경하지 않았다.

| 질문 | 캡처 판단 | 수정 |
|---|---|---|
| payments-service CPU 급증 | 대상·사실 수치는 적절하다. 단독 ‘가능성이 있습니다/확인하세요’는 정보가 없고, 도구로 배포 이력까지 볼 수 있다는 설명은 부정확하다. | 작성 지침과 공통 문장 필터 보완, 런북 원문의 도구 기능 수정. |
| 응답이 느려요 → cache-service야 | 되묻기와 이어가기는 정상이다. 설명에 빈 문장이 남는다. | 공통 필터 적용. 현재 메모리 값만으로 누수를 확정할 수 없다고 런북에 명시. |
| billing-service 응답 지연 | 미등록 안내가 적절하다. 임의 서비스 조회가 없다. | 기존 동작 유지. |
| DB 다운 절차 | db-down 검색은 적절하다. 일반 절차에 ‘관측 사실 없음’과 원인 후보·재작성 흐름이 붙는 것은 불필요하다. | 일반 절차는 검색 후 바로 전체 런북을 표시. 현재 DB 장애 진단이 아님을 명시. |
| payments-service와 cache-service 상태 | 관측 사실은 분리되어 있다. 서비스마다 2개 문서를 무조건 보여주면서 관련성이 낮은 증상이 섞였다. | 복수 서비스는 각자의 첫 알림에 한국어 절차 문맥을 붙여 검색하고 임계값을 통과한 대표 런북 1개만 선택. 알림이 없으면 보류. |
| 이름 소개 → 이름 회상 | 문자열은 기억했지만 ‘저는 기준입니다’로 화자를 혼동했다. | 흔한 소개·회상은 같은 대화의 사용자 발화만 읽고 ‘기준님’으로 답변. 다른 대화의 이름과 assistant 발화는 사용하지 않음. |

## 확인과 해석

- 표준 라이브러리 자동 테스트 21개 통과. 이번 결함의 재현 조건과 기존 대상 확인·부분 실패·오래된 값·SSE 초안 차단을 함께 확인했다.
- 실제 로컬 MCP·qwen3.5:2b·bge-m3로 6개 시나리오·8개 발화 확인을 통과했다. 결과는 [실제 실행 기록](../results/screenshot_fix_smoke.md)과 같은 이름의 JSON에 저장했다. 인프로세스 서버 핸들러로 확인했으며 수정 후 브라우저 자동화 검사는 아니다.
- CPU 질문은 cpu-spike, 복수 서비스는 cache의 memory-leak과 payments의 cpu-spike를 분리해 선택했다. 단일 cache 지연 질문은 high-latency를 선택했다. 이 선택은 질문의 지연 증상에 대한 참고 절차이며 실제 p95나 누수를 확인했다는 뜻은 아니다.
- 영문 알림만 사용한 초기 재확인에서 cache 문서가 점수 미달로 누락되고 payments에 지연 문서가 선택됐다. 실제 임베딩 점수를 대조한 뒤 대표 첫 알림과 한국어 절차 문맥으로 보완해 최종 복수 서비스 확인을 통과했다. 유사도 점수나 6개 사례의 통과를 일반 정확도로 해석하지 않는다.
- `memory-leak` 등은 검색된 참고 문서명이다. 메모리 누수나 공통 원인을 확인했다는 의미는 아니다.
- 현재 모니터링은 실습용 합성 데이터에 jitter를 더한다. 질문마다 수치가 달라지는 것은 정상이다. 배포 이력·로그·p95·시간별 추세 조회 기능은 구현하지 않았다.
- 대표 문서 1개, 단순 이름 패턴, 복수 서비스의 첫 알림 중심 검색은 의도적인 축소다. 알림의 심각도 순위를 계산하지 않으며 모든 복합 장애·대화 표현을 처리한다고 주장하지 않는다.
- 변경 반영에는 백엔드 재시작이 필요하다. 실행 중인 사용자 서버는 종료하지 않았다.
